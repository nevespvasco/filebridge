# 06 — Interface

App: `apps/desktop` (Tauri 2 + Vue 3 + TypeScript + Vite, Pinia stores).

A 5-step wizard for new sends and a job list to follow them. **The user never sees a terminal**;
whoever wants to can see the equivalent commands in a "Details" panel.

> **Design work in progress.** The visual language, the navigation (a Home screen, tabs on
> Transfer detail) and the next screens (transfer queue, files of a transfer, job log, report
> export, destination storage and browser) are specified in [design/](design/README.md). Those
> specs are *Proposed*; this doc stays the reference for what is built.

## "New transfer" wizard

1. **Source** — drag files and folders, or pick in the file explorer. Shows the running total
   (files and GB) while counting (`ScanProgress` events).
2. **Destination** — choose a profile (e.g. "Nextcloud home — demo/Backup") or create one.
   Shows free space and estimated time.
3. **Analysis** — problems found, grouped by rule ("312 names with decomposed accents — fix
   automatically"). Only items that need a decision stay pending; Send is disabled until none are.
4. **Review & send** — final summary (files, size, renames, mode), option "verify by checksum at
   the end", and the Send button.
5. **After transfer** — integration running ("Indexing in Nextcloud: 3 folders") and final report.

## Other screens

| Screen | Shows |
|---|---|
| Jobs | List of sends: state, progress, speed, ETA, automatic retries. A scheduled run says "Scheduled" (its detail links to Schedules), and a file whose older version was kept at the destination shows the kept name |
| Job detail | Current file, errors, log, manifest, Pause / Resume / Verify buttons |
| Destinations | Saved profiles, connection test, Nextcloud mode. For an SSH destination, a failed test or space check, and Browse, first check each server's host key: an unknown one gets the "Trust this server?" prompt (ADR 0015) and what failed runs again; a changed one is only shown as an error |
| Integrations | Active plugins and their settings |
| Repair destination | Analyse and fix names in an existing remote folder |
| Schedules | Scheduled sends ([ADR 0019](adr/0019-scheduled-sends.md)): one card per schedule (recurrence in words, sources → destination, next run, last run and its outcome with a link to its transfer, files sent so far), with On/Off, Run now, Edit and Remove (asks first; its runs stay). New/Edit: files and folders, destination, folder there, "On days" (weekdays + time) or "Every few hours" (N hours from a time), verify, and what a run does (only what changed, older versions kept, waits for the send hours). Sources, destination and folder can't change once saved |
| Settings | Bandwidth limit and send window (kept by the service, ADR 0010), notifications, language (pt and en) |

## Principles

- **Written for someone who isn't technical.** Each wizard step opens with one plain sentence
  saying what to do now; a disabled button says why it is disabled; jargon (SSH key, NFC,
  checksum…) gets a `HelpTip` ("?") with an explanation and an example; every form field shows a
  hint with an example under it; empty screens say what to do next and offer the button for it.
- **OS notification** on completion or error.
- **Closing the window doesn't stop the send** — tray icon stays.
- **Every destructive action asks for confirmation** and shows what will happen.
- **"Details" panel** in every job and wizard step: the equivalent commands (`rclone …`,
  `occ files:scan …`), for transparency and debugging. Never shows secrets.
- Long lists (hundreds of thousands of entries) are virtualised and paginated from SQLite, never
  loaded fully into the UI.

## Front-end structure (planned)

```
apps/desktop/src/
├── views/            # NewTransferWizard/, Jobs, JobDetail, Destinations, Integrations, Repair, Settings
├── components/       # ProgressBar, IssueGroup, BytesDiff, FileDropZone, DetailsPanel…
├── stores/           # Pinia: jobs, profiles, wizard, settings
├── bindings/         # generated by tauri-specta (DO NOT EDIT)
├── i18n/             # pt.json, en.json (vue-i18n)
└── main.ts
```

- All calls go through the generated `bindings/` (commands) and typed event listeners. No
  hand-written `invoke('...')`.
- `stores/jobs` subscribes to progress events once and keeps a normalised map by job id.

## Tauri commands (first draft)

| Command | Purpose |
|---|---|
| `scan_sources(paths)` | Start stage 2 for a draft job; returns job id |
| `list_profiles()` / `save_profile(p)` / `test_profile(id)` | Destinations screen & wizard |
| `get_issues(job_id, rule?, page)` / `decide_issue(issue_id, decision)` / `decide_all(job_id, rule?, decision)` | Analysis step |
| `set_options(job_id, options)` | Review step: change "verify" etc. without a new analysis (refused for a Repair job: its folder is what the user confirms) |
| `start_job(job_id, options)` / `pause_job` / `resume_job` / `cancel_job` / `verify_job` | Lifecycle |
| `skip_entry(job_id, idx)` | Transfer detail: leave one file not sent yet out of a started send (implemented: design D04) |
| `list_jobs()` / `get_job(job_id)` / `get_job_log(job_id, page)` | Jobs screens (the log is `job_log(job_id, after_id, before_id, limit)`, implemented: design D07) |
| `create_repair_job(profile_id, dir)` (as built; then `analyse`, the decisions and `start`, like a send), `planned_renames(job_id)` (what the confirmation counts) | Repair destination; "Continue" and "Send again" on a repair open this page, never the New transfer wizard |
| `get_settings()` / `save_settings(settings)` | Settings: app-wide bandwidth limit and send window (implemented) |
| `service_log()` | Settings → "Copy log": the engine's recent log lines, secrets scrubbed, for bug reports (implemented: design D07) |
| `list_schedules()` / `save_schedule(input)` / `delete_schedule(id)` / `run_schedule_now(id)` | Schedules (implemented, ADR 0019); the `schedule_ran` event refreshes the list |
| `remove_access(profile_id)` | "Remove access" wizard |
