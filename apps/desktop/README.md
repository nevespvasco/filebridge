# apps/desktop

Tauri 2 + Vue 3 + TypeScript + Vite desktop app. **Landed in:** Phase 1 (Wave 3, step 3b).

## Responsibility
- `src/` — the interface: the 5-step "New transfer" wizard, Jobs, Job detail, Destinations,
  Settings. Pinia stores, vue-i18n (pt, en). Integrations and Repair destination come later.
- `src-tauri/` — Tauri commands and events. **A thin client of `filebridge-service`** over
  `crates/ipc` ([ADR 0008](../../docs/adr/0008-service-ipc.md)): no business logic here. Starts the
  service if its socket is missing, manages the tray icon and the "Start the engine when I log
  in" switch. The installed app carries `filebridge-service`, the `filebridge` CLI and rclone as
  sidecars ([Bundle](#bundle-one-install-no-terminal)).

## Rules
- All Rust ↔ TS types come from `tauri-specta` into `src/bindings/` — never hand-written.
- Closing the window never stops a send.
- Destructive actions always confirm and show what will happen.

## Layout
```
src/
├── bindings/index.ts   generated by tauri-specta (DO NOT EDIT)
├── lib/                api.ts (unwraps command results), platform.ts (picker, drop, notifications), format.ts

├── views/              NewTransfer/ (Step*.vue), Jobs, JobDetail, Destinations, Settings
├── components/         IssueGroup, BytesDiff, FileDropZone, JobProgress, PreflightList, DetailsPanel,
│                       HelpTip (the "?" with a plain explanation and an example), …
├── i18n/               pt.json, en.json (same keys)
└── dev/mock.ts         fake service for `VITE_MOCK=1` (never bundled); one typed handler per
                        command in the bindings, state rules from `JOB_OPERATIONS`
src-tauri/src/
├── lib.rs              builder, tray, close → hide, bindings export
├── commands.rs         one command per operation in the ipc catalogue (generated), plus the window's own
├── service.rs          connect / start the service / forward events / reconnect
└── tray.rs
```

## Talking to the service
- The window connects to `FILEBRIDGE_SOCKET` if set, else `Endpoint::default_for_user()`
  (`$XDG_RUNTIME_DIR/filebridge/service.sock`, else in this user's cache directory, or a named
  pipe on Windows). A service there run by another user is refused, and reported rather than
  replaced by starting one.
- If nothing listens there it starts `filebridge-service`: `FILEBRIDGE_SERVICE` if set, else the
  binary next to the app's own executable (the bundled sidecar: Tauri installs `externalBin`
  beside the app, `/usr/bin/` in the .deb and .rpm; `target/debug/` in development), else
  `PATH`. The service finds rclone the same way: `--rclone`/`FILEBRIDGE_RCLONE`, else next to
  its own executable (the bundled `filebridge-rclone`, then an `rclone`), else `PATH`, else
  `~/.local/bin/rclone` (`filebridge_host::find_rclone`). It waits up to 5 s for the socket. The child gets its own process group, so it
  outlives the window and a Ctrl+C in the terminal that ran `tauri dev`.
- `ping` checks `PROTOCOL_VERSION`. A service with an **older** protocol (left running by an
  earlier version of the app) is replaced, on Unix, in this order:
  1. the service binary is found first; with none, the old service is left running
     (`incompatible_service`);
  2. one connection gives the peer's pid (checked to be `filebridge-service`) and answers a
     `ping` on that same connection: when it already speaks the protocol (another window
     replaced it a moment ago) it is left alone and used;
  3. how it was started is read (Linux: `/proc/PID/cmdline`, `environ`, `cgroup`). One started
     with arguments other than `--data-dir`, `--rclone`, `--socket`, `--fake-transport` and
     `run` is not replaced: the error says why and to quit it. Other Unixes replace only a
     service started without arguments;
  4. SIGTERM (running jobs are stored as they are and resume in the new service), up to 10 s
     for the socket to go quiet, then the new one starts with the same `--data-dir`, `--rclone`,
     `--socket` and the old process's `FILEBRIDGE_*` variables (and none of this window's).
     One run by the systemd user unit `filebridge-service.service` (its cgroup says so) is
     instead restarted by systemd: the window runs `systemctl --user restart
     filebridge-service.service` (up to 10 s), which stops it the same way and starts the
     binary in the unit's `ExecStart` (the one an update of the app replaced), then waits up
     to 5 s for the socket to answer, as for a service it starts;
  5. if the new one still speaks an older protocol, the binary on disk is old too: the window
     remembers it and never stops and restarts it again (until it is reopened). For the unit
     the error names the old binary its `ExecStart` runs and says to use "Update" under
     "Start the engine when I log in" in Settings, which points the unit at this app's service.

  From step 4 to the new one answering (up to 10 s plus 5 s) every command waits. The window
  emits `connection-changed { connected: false, replacing: true }` before step 4, and the
  window-only command `serviceReplacing` says the same to a window that starts listening later;
  the banner and the status then read "Updating the copy engine…" instead of an error. It ends
  with `connected: true`, or `connected: false, replacing: false` when the replacement failed.

  A **newer** service is never stopped. Any mismatch left is the error code
  `incompatible_service`. A missing binary or a service that never answers is
  `service_unavailable`. Windows: the user quits the old service.
- `tauri dev` runs `cargo build -p filebridge-service` first, so the service started from
  `target/debug/` is always the current one.
- Events: `Client::events()` is forwarded as the Tauri event `service-event` (payload: the engine
  `Event`). The stream ends (`Closed`) when the connection drops; the window then emits
  `connection-changed { connected: false, replacing: false }`, reconnects with backoff (starting the service again
  if needed) and emits `connected: true`, on which the stores reload, since events sent in
  between are lost.
- Commands (camelCase in TS): `ping`, `listProfiles`, `saveProfile`, `deleteProfile`,
  `testProfile`, `detectNextcloud`, `createJob`, `setOptions`, `analyse`, `ruleCounts`, `issues`,
  `decide`, `decideAll`, `start`, `pause`, `resume`, `cancel`, `listJobs`, `job`, plus window-only `serviceEndpoint`,
  `serviceReplacing`, `setTrayLabels`, `autostart` and `setAutostart`. Started with
  `--start-engine` the app only starts the service and exits (the Windows login entry). They return `{ status: "ok", data } | { status: "error", error: ErrorBody }`;
  `api.*` in `src/lib/api.ts` turns that into a value or a thrown `ServiceError` with its `code`.

## Start the engine when I log in
A switch in Settings (pt/en), backed by the per-user login entry of each desktop OS
([ADR 0028](../../docs/adr/0028-login-start-on-every-desktop-os.md)): the `systemd --user` unit
`~/.config/systemd/user/filebridge-service.service` on **Linux**, the LaunchAgent
`~/Library/LaunchAgents/app.filebridge.service.plist` on **macOS**, the value
`filebridge-service` under `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`
on **Windows**. The service binary is what writes and removes it: the window's `autostart` /
`setAutostart` commands (`src-tauri/src/autostart.rs`) run the same `filebridge-service` the
window would start, with `show-user-unit --json` (`filebridge_ipc::UserUnit`: which `kind`,
where it lives, the program it runs, installed, enabled, current, its contents),
`install-user-unit --no-start` and `uninstall-user-unit`. Not an ipc request: it works with no
service running, and the window never touches the entry itself.
- Turning it **on** shows where the entry goes, the program it runs and the entry itself (the
  unit file, the plist, or the Run value's command line), then writes and enables it. Not
  started now: the engine running now holds the data folder and keeps running; the OS starts
  it from the next login.
- Turning it **off** says what stops, then runs `uninstall-user-unit`. On Linux and macOS
  systemd / launchd stop the engine they started (jobs stay stored) and the window starts its
  own at once, as after any dropped connection; on Windows removing the Run value stops
  nothing.
- An entry that runs another binary or other options (installed earlier from a terminal, or
  from another build) shows "Update", which rewrites it.
- **Windows:** the service is a console program, so the window passes itself as `--launcher`
  and the Run value starts the app with `--start-engine` (`filebridge_ipc::START_ENGINE_ARG`,
  handled first thing in `lib.rs`): it starts the service as the window would
  (`service::start_engine`, no window, nothing if one already answers) and exits.
- Shown off with the reason when it can't work: an **AppImage** (its files are gone once it
  exits, so the entry would point nowhere; the service refuses too), no `filebridge-service`
  found, no systemd user session, or no launchd desktop session. Hidden on phones.
- *macOS and Windows are unit-tested but not yet run on those systems.*

## Bundle: one install, no terminal
`pnpm bundle` (`tauri build --config src-tauri/tauri.bundle.conf.json`) makes the installers
(`.deb` and `.rpm` on Linux; Tauri's defaults on Windows and macOS) with three sidecars beside
the app's own binary:
- **`filebridge-service`**, built in release for the target;
- **`filebridge`**, the CLI ([apps/cli](../cli/README.md)), at `/usr/bin/filebridge` in the
  packages, which also install its man pages and bash/zsh/fish completions
  (`bundle.linux.deb.files` / `rpm.files`);
- **rclone** as `filebridge-rclone`, the version pinned in
  [`sidecars/RCLONE_VERSION`](../../sidecars/RCLONE_VERSION) (the one librclone is built from on
  phones). Its own name because Tauri installs sidecars in `/usr/bin`, where `rclone` would
  clash with the distribution's package and shadow the user's own. Its MIT licence goes in the bundle as
  `licenses/rclone-COPYING.txt` (a resource: `/usr/lib/filebridge/licenses/` in the .deb).

`tauri.bundle.conf.json` adds `bundle.externalBin`, `bundle.resources`, the packages' extra
files and a `beforeBuildCommand` that runs `scripts/prepare-sidecars.mjs` before `pnpm build`:
[`sidecars/prepare-desktop.sh`](../../sidecars/prepare-desktop.sh), or `prepare-desktop.ps1` on
Windows. The script builds the service and the CLI and copies the pinned rclone (downloaded and
checked against its release's `SHA256SUMS` with `RCLONE_DOWNLOAD=1`, else from `RCLONE`, `PATH`
or `~/.local/bin` after checking `rclone version`; see [sidecars](../../sidecars/README.md)) to
`sidecars/bin/<name>-<target triple>`, the names Tauri looks for. They live in a separate config on purpose: tauri-build
copies every `externalBin` into `target/` on each `cargo build`, so in `tauri.conf.json` they
would make `cargo test`, clippy and `tauri dev` need the files and overwrite the
`target/debug/filebridge-service` that `tauri dev` builds.

```bash
pnpm bundle                       # .deb and .rpm (tauri.linux.conf.json)
RCLONE_DOWNLOAD=1 pnpm bundle     # the same, with the pinned rclone downloaded and checked
sudo apt install ../../target/release/bundle/deb/filebridge_0.3.0_amd64.deb
```
**No AppImage.** `tauri.linux.conf.json` limits the Linux targets to `deb` and `rpm`. Tauri
builds an AppImage only after downloading linuxdeploy, its AppRun and its GTK plugin from
GitHub (the moving `continuous` releases, with no checksum) and running them, so it can't be
built offline and would run unverified tools, against the rule the rclone download follows.
And an AppImage can't start the engine at login (its files are gone once it exits). `pnpm
bundle --bundles appimage` still asks Tauri for one, on a machine where that is acceptable.
After installing, filebridge opens from the app menu; it starts the service by itself, and
Settings → "Start the engine when I log in" keeps it running across logins.

## TypeScript bindings
- Generated, never edited: `pnpm bindings` (runs the `export_bindings` test), and on every debug
  run of the app. Commit the result.
- specta-typescript 0.0.13 refuses 64-bit integers. The export uses tauri-specta's
  `dangerously_cast_bigints_to_number()`, a `specta_util::Remapper` rule set that maps
  `u64`/`i64`/`usize`/`isize`/`u128`/`i128` to `number`. That is safe here: they are byte counts,
  file counts, issue ids and millisecond timestamps, all far below 2^53.
- `serde_json::Value` (`Profile.integration_settings`) exports as the recursive JSON type `Value`.
  Its `Number` variant also goes through the same remap. Because `Value` is deep, keep it out of
  deep `ref()`s (`shallowRef`, see `stores/profiles.ts`).
- Types whose serde shape differs by direction come as `Foo_Serialize` (what commands return) and
  `Foo_Deserialize` (what they accept, where `Option` fields may be left out).

## Window behaviour
- Closing the window hides it; the tray icon (left click or "Open filebridge") brings it back.
  The tray's other item closes the window process only, and sends keep running in the service.
  Tray labels follow the UI language (`setTrayLabels`).
- OS notification when a job finishes or fails (`job_finished`), unless turned off in Settings.
- Long lists: issues are paged from SQLite with `after_id` (100 per page, cursor stack for
  "Previous"); the Jobs list pages with `limit`/`offset`.

## Development
```bash
pnpm install
pnpm tauri dev          # needs the Tauri system libraries (Linux: webkit2gtk-4.1 and friends)
FILEBRIDGE_FAKE_TRANSPORT=1 pnpm tauri dev   # the real service and engine, no rclone: profiles
                                             # use transport "fake" and a local root
VITE_MOCK=1 pnpm dev    # UI only, in a plain browser, against src/dev/mock.ts (visual work)
VITE_MOCK=1 VITE_MOCK_EMPTY=1 pnpm dev   # the same, starting like a new user (no destinations, no jobs)
VITE_MOCK=1 VITE_MOCK_OFFLINE=1 pnpm dev # the same, with a copy engine that never starts
pnpm build              # vue-tsc + vite build
pnpm bindings           # regenerate src/bindings/index.ts
pnpm bundle             # installers with the service and rclone inside (see Bundle)
```
Linux packages for `tauri dev` / `tauri build`:
`libwebkit2gtk-4.1-dev libgtk-3-dev libayatana-appindicator3-dev librsvg2-dev libsoup-3.0-dev`.
